usfm_onion

A Rust engine for USFM — the markup format the global Bible-translation community uses to author scripture. One canonical working model (flat tokens). Everything else is a layer over it.

The engine parses USFM, projects it into a source-faithful concrete syntax tree, lints and formats it, diffs versions of it, and exports it to USJ, USX, HTML, and verse-reference maps. It runs natively in Rust and in browsers via a wasm-pack wrapper. The same logic drives both.

Design contract
Parse once, operate on tokens. A flat Vec<Token> is the working representation; every operation reads or rewrites that stream. Never silently normalize on ingest. If the source has odd whitespace, duplicate \id, or unclosed markers, the parser preserves the bytes; lint surfaces the problems; format proposes fixes; exports apply spec-defined recovery and say so.

Mental model#

  1. Tokens are the truth. parse(source) produces a Vec<Token> that round-trips back to the original bytes exactly via tokens_to_usfm. No normalization, no synthesised whitespace.
  2. Operations consume tokens. Lint, format, diff, and the CST projection all read tokens. The CST is a tree view over the same stream; it never invents content and always flattens back to canonical tokens.
  3. Exports are explicitly lossy. USJ, USX, HTML, and verse-reference maps are downstream projections. They apply spec-defined recovery (closing unclosed footnotes at block boundaries, for example) and cannot round-trip back to source.

Pipeline#

The walker is a single state machine that every structural consumer drives through, so each output format only concerns itself with output-specific concerns. Format and diff sit beside the walker as token-stream rewriters.

Lossless foundation#

The first three layers are byte-faithful. They never invent, drop, or merge bytes.

LayerProducesRound-trips?
lexerVec<Lexeme> with byte spansyes
parseVec<Token>, plus id/sid assignment and attribute liftingyes — tokens_to_usfm
cstCstDocument — a source-faithful tree projected from tokensyes — flattens back to canonical tokens

Tokens and the CST coexist

The flat stream is the source of truth. The CST is a view derived from it. Both are useful for different operations:

  • Tokens give exact spans and exact whitespace — the right shape for lint, format, and diff, which need to point at specific bytes and rewrite ranges.
  • The CST gives structural nesting — the right shape for any consumer that asks "what is the parent of this verse?" or wants to traverse the document as a tree.

The CST is always derivable from the tokens; the tokens are never derived from the tree.

The walker#

The walker is a single visitor-based state machine over the flat token stream. It owns the scope stack, applies USFM's marker-precedence rules, and emits events. Every structural consumer (CST, USJ, USX, HTML, vref, lint) is a visitor — it overrides the events it cares about and ignores the rest. Each output format concerns itself only with its own output specifics.

The visitor surface

pub trait Visitor<'tokens, T: WalkableToken> {
    fn on_enter_scope(&mut self, ctx: &WalkContext, frame: &ScopeFrame, token: &T, i: usize) {}
    fn on_leave_scope(&mut self, ctx: &WalkContext, frame: &ScopeFrame, reason: LeaveReason) {}
    fn on_end_marker(&mut self, ctx: &WalkContext, token: &T, i: usize) {}
    fn on_text(&mut self, ctx: &WalkContext, token: &T, i: usize) {}
    fn on_chapter(&mut self, ctx: &WalkContext, token: &T, i: usize) {}
    fn on_verse(&mut self, ctx: &WalkContext, token: &T, i: usize) {}
    // + on_book_code, on_milestone, on_milestone_end, on_opt_break, on_newline, on_other
}

pub fn walk_tokens<'tokens, 'src, V>(tokens: &[Token<'src>], visitor: &mut V)

WalkContext is a live view of the scope stack handed to every callback. ScopeFrame describes one open scope: what marker opened it, where in the token slice the opener lives, what paragraph category / inline context / note context applies, and the kind of scope it is (Block, Note, Character, Milestone, Chapter, Verse, TableRow, TableCell, Sidebar, Periph, Header, Meta, Unknown).

Scope stack & events

Opening \p after an unclosed \f closes the Note, the prior Verse, and the prior Block. The walker annotates each pop with a LeaveReason; consumers that just want a clean tree (USJ, HTML) ignore the reason, lint subscribes to RecoveryClosure as its "unclosed note" signal.

Event types

EventFires on
on_enter_scopeA marker opens any scope (chapter, verse, paragraph, note, character marker, sidebar, milestone-start, table row/cell, header, meta, periph).
on_leave_scopeA scope closes. LeaveReason is one of Explicit, RecoveryClosure, ImplicitByOpen, EndOfInput.
on_end_markerAn EndMarker token (\f*, \nd*, …). Fires after on_leave_scope(Explicit) so visitors that need to append the closer as a leaf can do so.
on_milestone / on_milestone_endSelf-closing milestone tokens and the \* closing a paired milestone.
on_chapter / on_verse / on_book_codeThe number/code token immediately following \c / \v / \id.

on_otherCatch-all for unknown markers, stray closers, numbers outside chapter/verse, anything the walker couldn't classify structurally.

The first six are walker-driven. Format and diff sit beside the walker — they operate on token streams directly.

Why format and diff aren't visitors

Format needs &mut [FormatToken] to rewrite tokens in place. The walker is read-only by design; mutating walks would double the visitor API for one beneficiary.

Diff operates above tokens — it builds SID-keyed chapter blocks and runs a diff algorithm over them. It never needs structural events; it needs already-tokenized chapter slices.

Recovery#

USFM in the wild is messy. Files have unclosed footnotes, unknown markers, paragraph markers nested where they shouldn't be. The walker applies spec-defined precedence rules so the structural interpretation is consistent across consumers; each pop is annotated with a LeaveReason so visitors can distinguish source intent from synthesised recovery.

Precedence rules

Each kind of incoming marker closes specific kinds of open scope before pushing its own frame. The cases:

Incoming markerWhat it pops
Chapter (\c)Everything. A new chapter resets the entire scope stack down to nothing.
Verse (\v)Inline scopes (Note, Character, Milestone), any prior Verse, then any Header / Meta above.
Block / paragraph (\p, \q, \li, etc.)Inline scopes + Verse, then prior Block / TableCell / TableRow / Header / Meta, then everything down to the nearest Chapter / Periph / Sidebar.
Sidebar (\esb)Everything down to the nearest Chapter.
TableRow / TableCellInline scopes + Verse + cell/row siblings, then down to TableRow / Chapter / Periph / Sidebar.
Header / Meta / Periph (\h, \toc1, etc.)Everything.
Note / Character / Milestone (\f, \nd, \zaln-s, …)Inside a note: pops the open Note if the incoming marker isn't valid inside it. Otherwise pushes without popping.
Unknown markerPops down to a structural parent (Chapter / Periph / Sidebar), then emits as on_other without pushing a frame.
End-of-inputDrains every remaining open frame.

LeaveReason on every pop

LeaveReasonMeans
ExplicitAn explicit closer arrived (\f*, \nd*, \zaln-e\*, \esbe).
RecoveryClosureA Note frame was synthesised closed because an opening marker satisfying the note-recovery predicate arrived. Lint subscribes to this as its "unclosed note" signal.
ImplicitByOpenThe pop was driven by precedence — a higher-level scope opened that the rules say must close this one.
EndOfInputThe token stream ended while the scope was still open.

Explicit closers fire two events

When \f* arrives, the walker fires on_leave_scope(reason: Explicit) and then on_end_marker with the closing token. Visitors that want the closer to appear as a leaf in their output (CST, USJ) handle it on on_end_marker; visitors that don't care (vref, lint) ignore it.

Compound bridge SIDs

A verse range like \v 1-2 produces a single SID covering both numbers. The vref export emits the bridged form ("GEN 1:1-2") rather than splitting; consumers that need per-verse text handle the split themselves.

Where recovery is applied
USJ, USX, HTML, and vref are lossy: they emit a clean tree / map shaped by the walker's recovery decisions. CST and lint observe the same events but they don't change what they output based on them — lint records a finding; CST records the close in its tree shape. The flat token stream itself is never modified.

Marker catalog#

USFM 3.2 defines hundreds of markers. The catalog is the single source of truth for marker metadata. Lint rules, the structural classifier, and the walker all consult it; nothing in the engine hardcodes marker names.

use usfm_onion::{marker_catalog, marker_info, is_known_marker};

let p = marker_info("p");
// p.kind            -> MarkerKind::Paragraph
// p.category        -> MarkerCategory::Body
// p.note_family     -> None
// p.inline_context  -> Some(InlineContext::Para)
// p.contexts        -> &[SpecContext::ChapterContent]
FileRole
src/marker_defs.rsType definitions (MarkerSpec, MarkerKind, StructuralScopeKind, ParagraphCategory) + lookup helpers.
src/marker_defs_data.rsThe actual rows. Tracks USFM 3.0 through 3.2.

Every row cites its spec source URL, so the provenance of any given marker's metadata is auditable from the row itself.

A marker whose opening form consumes an argument right after its name carries a payload: BookCode for \id, NumberRange for the chapter/verse family (\c, \cp, \ca, \v, \vp, \va). The same table (marker_defs::marker_payload) feeds both the catalog and the lexer, so what the catalog advertises and what tokenization expects cannot drift. On the JS side it surfaces as MarkerInfo.payload ("bookCode" | "numberRange").

Whitespace contract#

MARKER_WHITESPACE in marker_defs_data.rs declares, per marker:

  • what whitespace the spec requires at each position (before the marker, after the marker name, around the closing form);
  • what whitespace the formatter prefers when normalizing.

One table, two consumers: the formatter writes it, the linter flags violations against it. If a row says \c requires AtLeastOneHorizontalWhitespace after the marker name, then \c1 is a lint finding and the autofix is exactly what the formatter would insert — a single space.

The tag-end delimiter belongs to the marker

The first space after a marker name (\v␣1), after a chapter/verse number, or after an \id book code (\v 1␣In) is the tag-end delimiter — markup the syntax requires, not content. The parser absorbs that one required byte onto the owning token's span, so the tokens that follow are content-pure: a verse-text projection sees In the beginning, never a phantom leading space. Any whitespace beyond the single required byte flows forward to the next token, where lint can still see and flag it.

Why this doesn't break losslessness
The delimiter byte changes owner; it is never dropped. tokens_to_usfm(parse(s)) == s still holds exactly. Absorption is driven by the MARKER_WHITESPACE table — an opening marker absorbs only when its row requires trailing whitespace; closers, milestones, optional-whitespace and unknown markers never do, and a number absorbs only as the argument of \c/\v. "The token happens to end at a space" is deliberately not the test. Newlines are never absorbed.

Rust facade#

Three types in src/api.rs cover the surface. The difference comes down to when you parse:

TypeHoldsUse when
UsfmSource string only.You have a source string and want one or two operations on it. Each method on Usfm parses internally on call.
ParsedUsfmSource string + the parsed token vec (owned).You'll run several operations on the same document and want to pay the parse cost once. Usfm::parse_owned() produces it.
TokenStream<T>A Vec<T> for any token type implementing the relevant traits.You already have tokens — borrowed Token<'a> straight from parse, or owned FormatToken, or any other type that implements the public token traits.
use usfm_onion::{FormatOptions, HtmlOptions, LintOptions, LintScope, Usfm};

// One-off: each call re-parses internally.
let doc = Usfm::from_str(source);
let issues = doc.lint(LintOptions::scoped(LintScope::Book));
let html   = doc.to_html(HtmlOptions::default());

// Several ops on the same document: parse once, reuse the tokens.
let owned = doc.parse_owned();
let issues = owned.lint(LintOptions::scoped(LintScope::Book));
let formatted = owned.format(FormatOptions::default());

// You already have tokens (from your own data model, or a prior parse).
use usfm_onion::{TokenStream, parse::parse};
let parsed = parse(source);
let stream = TokenStream::from_tokens(parsed.tokens);
let issues = stream.lint(LintOptions::scoped(LintScope::Book));

The library is string-in, data-out. It does no file I/O and does no parallelism — both belong to callers. For an example of parallelizing across a whole corpus, see the parallelism benchmark, which uses rayon at the file level.

Lint requires a scope
LintOptions has no Default — the caller must declare what slice it is linting via LintScope: Front (the pre-\c book matter), Chapter(n) (one chapter), or Book. Document-level rules (missing/duplicate \id, id-position, content-before-first-chapter) run only for Front and Book; under Chapter they are suppressed, so a mid-book chapter relint can't falsely report a missing id. LintOptions::scoped(LintScope::Book) reproduces whole-document linting. A USFM file is one book; cross-book and cross-project consistency are deliberately a consumer concern, not this library's.

Resident corpus#

Everything above this section is stateless: you hand it a string or a token array and it hands back an answer. That is the right shape for a one-shot conversion and the wrong shape for an editor, which holds a whole project open, changes one chapter at a time, and needs to know what moved. The resident subsystem is the stateful half.

Four crates, one direction of dependency, and no crate learns another's job:

CrateOwnsNever owns
usfm_onionUSFM semantics: lexer, parser, tokens, lint rules, format, diff, projectionsresident state, byte layouts, JS shapes
usfm_onion_wireThe packed container format, its checked codec, the trust boundary, and the boundary DTOslifecycle, dirty state, rule execution
braidThe resident corpus: ordered books, validated mutation, hashes, staleness, snapshots, patches, baselinesbyte layouts, IO, scheduling
usfm_onion_wasmThe JS boundary, and the composition of the two crates that must not know each othera second copy of anything

braid depends on usfm_onion and never on usfm_onion_wire: a resident corpus does not know what a byte offset is. So composing them — publishing a corpus as packed bytes, or seeding one from packed bytes — happens in the wasm crate, which is the only layer permitted to know both.

The caller contract

Mutate, then hydrate what changed:

const effect = braid.updateChapter(target, { kind: "tokens", tokens });
if (effect.status === "ok") {
  for (const scope of braid.toTokens(effect.value.changed).value) {
    // reconcile scope.tokens
  }
}

Every mutating verb applies before it returns, so a read after a mutation is always consistent, and a rejected mutation leaves state provably untouched — same snapshot id, same per-book hashes. Effects are plain values, not subscriptions: nothing tracks per-consumer cursors. A consumer that defers hydration keeps its own pending list, and toTokens normalizes whatever it is handed (duplicates collapse, a whole-book scope absorbs that book's chapter scopes), so naive accumulation across several effects is always correct.

Tokens enter in exactly three places — replaceCorpus, updateBook, updateChapter — the moments the caller knows something the corpus does not. No other verb accepts caller tokens. Source bytes, hashes, and chapter runs are always derived from tokens, never the other way round.

Identity

StampCoversWhy it exists
snapshotIdThe ordered per-book source hashes, and nothing elseCorpus identity. Deterministic across processes: the same bytes in the same order always give the same id, so a publication and a restore agree without coordinating.
sourceHashOne book's exact bytesBinds a packed section to the source its spans index into.
tokenIdentityEverything a book's tokens carry that its bytes do notA book's bytes are its tokens' text concatenated, so byte-identical content can carry entirely different stable ids, anchors, or attribute spellings. A consumer caching anything token-derived keys on this, not on the source hash.

Lint results additionally carry a configuration fingerprint and a rule-engine stamp. A cached result is adopted only when all of them agree; the engine stamp includes the crate version, so a release invalidates every warm cache by design rather than risking a stale finding.

Explicit recompute

lint() is the only verb that runs rules, and it runs them for exactly the books whose content or configuration changed. A clean corpus runs none. No mutation lints implicitly, and no effect carries findings — findings are always something you asked for. The same is true of vrefIndex(scope), which caches per chapter run: after a one-chapter edit, reading the whole book's verse index recomputes that chapter and takes the rest from cache.

Fixes and formatting are patches

A lint finding may carry a fix. Braid resolves it against the current snapshot into a patch — a run of token operations addressed by (snapshot, ordinal) — which you can inspect, preview, or apply. Preview is a pure projection and mints nothing; identity is granted only when a token becomes resident. Staleness falls out of the identity: a patch resolved against a corpus that has since moved is refused rather than applied to the wrong tokens, which matters because two findings can legitimately propose different edits to the same token. Formatting works the same way, at scope grain.

Publication and warm open

A resident corpus publishes as one packed container: token and finding sections per book, the snapshot id, and — when the findings are meant to be reusable — the stamps that license reusing them. Republication reuses the encoded sections of books that did not change, splicing them rather than re-encoding, and a reused section is re-validated before adoption, so reuse never means trust.

restoreCorpus is the reverse: verify the bytes, seed the corpus, and skip the lex and parse entirely. Residency and lint-priming are independent — a book whose cached findings cannot be adopted still seeds, and is simply awaiting recompute.

WASM surface#

crates/usfm_onion_wasm wraps the library for browser and Node consumers. Every public type is tsify-derived — TypeScript declarations come straight from the Rust definitions.

The stateless exports below take caller-owned strings and tokens. The resident Braid class (see Resident corpus) takes resident scopes and never arbitrary external tokens. That split is deliberate even where both reach the same core function, because "operate on what I gave you" and "operate on what you are holding" are different promises.

Verbs that can be refused return a tagged result rather than throwing: { status: "ok", value } | { status: "error", error }, with a discriminated error union a consumer switches on. Exceptions are reserved for programmer errors. Declarations name a per-verb alias (PatchMutationOutcome and friends) because wasm-bindgen erases a generic's parameters in a method signature; each alias resolves to the instantiated result type.

The vref index is a content-byte-lossless projection of each verse: { sid → { text, segments } }, where every Segment maps a UTF-16 range of text back to both a source byte span and the originating token id. It exists so a node-based consumer (the editor's DOM, keyed by data-id) can translate between projected verse text and the tokens that produced it — finding-highlighting without re-deriving offsets. With the tag-end delimiter now owned by its marker, those joins are content-pure (no leaked delimiter space). Unlike toVref (a flat, lossy string map), the index round-trips content bytes and is the surface for offset-mapping consumers.

Why some ops are token-in and others aren't
Lint, format, and diff are the operations a caller is most likely to run repeatedly on the same document (e.g. validating on every change to a buffer). Token-in entry points let those callers skip a re-parse on each call. The vref index joins them — vrefIndexTokens exists because the editor re-derives it on every edit from tokens it already holds. USJ, USX, HTML, the flat vref map, and CST are typically one-shot per document, so they stay string-in only — adding a parallel token-in surface would just double the API for no real-world payoff. The surface is intentionally minimal.

JS token shape#

The Token type a JS caller passes to lintTokens / formatTokens / diffTokens is the same shape ParsedUsfm.tokens() returns. Field names are camelCase; enums are JS string unions. Schematically:

type Token = {
  id: string;                  // stable token identity
  kind: "marker" | "endMarker" | "milestone" | "milestoneEnd"
      | "bookCode" | "number" | "text" | "newline" | "optBreak";
  source: string;              // literal source slice; on a marker/number/bookCode it includes the absorbed tag-end delimiter
  marker?: string;             // e.g. "p", "v", "f", "nd"
  nested?: boolean;            // "+"-prefixed nested character marker
  span?: { start: number; end: number };
  sid?: string;                // e.g. "GEN 1:1" — set on chapter/verse openers
  attributes?: AttributeItem[]; // |key="value" list on character markers
  structural?: {              // present on marker / endMarker / milestone tokens
    scopeKind: "block" | "note" | "character" | "milestone"
              | "chapter" | "verse" | "tableRow" | "tableCell"
              | "sidebar" | "periph" | "header" | "meta" | "unknown";
    inlineContext?: InlineContext;
    noteContext?: SpecContext;
  };
  numberInfo?: [number, number | null, NumberRangeKind];
};

If you produce tokens from your own data model — converting a tree, normalizing a draft, replaying edits — fill in id, kind, source, and whichever optional fields apply to your token type. The walker only needs kind, marker, source, and structural; lint and diff additionally look at span, sid, id, and numberInfo. Concatenating every token's source in order reproduces the original bytes — that is tokensToUsfm.

Pattern: lint without re-parsing

import { parse, lintTokens } from "usfm-onion-web";

const doc = parse(source);
const tokens = doc.tokens();

// Repeated lint calls on the same tokens — no second parse, no marshalling overhead.
// scope is required: "book", "front", or { chapter: n }.
const issues = lintTokens(tokens, { scope: "book" });

// Mutate one chapter in your editor, then re-lint just that chapter:
const nextIssues = lintTokens(chapterTokens, { scope: { chapter: 5 } });

Stability contracts#

Three Rust traits define the minimum token surface each operation needs. On the JS side they collapse into "the Token shape" above — JS callers don't see the traits directly, but the trait surface is what determines which fields a caller must provide.

WalkableToken

Required by the walker. Implemented for every token type that flows through any structural consumer.

Needs: kind, marker, source, and structural (present on marker-family tokens; absent elsewhere).

LintableToken

Supertrait of WalkableToken. Required by lintTokens.

Adds: span, sid, id, numberInfo.

FormattableToken / DiffableToken

Standalone. Format needs mutable accessors. Diff needs SID accessors.

Both accept the same Token shape from JS.

The stable JS-facing strings (LintCode, FormatRule) are derived from Rust enums via tsify, so a new lint code appearing on the Rust side surfaces automatically as a new member of the string union in the generated .d.ts.

Parametric codes
A handful of codes carry kind / target / location params that distinguish closely-related cases — e.g. content-before-first-chapter has kind: paragraph | verse; unclosed-marker has kind: note | character | other and location: at-eof | at-boundary. Scope, and what lint does not check
Every rule is either chapter-invariant (fires only on a pattern present within the slice — most rules) or document-level (the four Document-category codes above: missing/duplicate \id, id-position, content-before-first-chapter). Document codes run only under Front / Book scope, never Chapter(n) — so a consumer can lint one chapter without a spurious missing-id, and the same finding for a chapter agrees whether it was linted alone or inside the whole book. Three former rules — chapter-expected-increase-by-one, verse-expected-increase-by-one, inconsistent-chapter-label — were removed: non-sequential chapters/verses (bridges, omitted verses) and label variation are valid USFM, so they are consistency heuristics, not markup validity. Uniqueness still counts (duplicate-* stays): two \v 5 make an ambiguous address. Consistency belongs to a consumer or to scripture-sous-chef, not here.

VREFVerse-keyed text extraction (search indexes, alignment tools).Drops everything but the verse text. (The vref index — see WASM surface — is the content-lossless counterpart with a segment map back to tokens.)

All four route through the walker for structural traversal — the shared recovery contract lives in one place so behavior is consistent across export formats.

Tips for consumers#

If you're calling from the browser

Parse once, lint many. If you're going to run lint repeatedly on the same document (validation on edit, debouncing, etc.) call tokens() once and pass the resulting array into lintTokens on each subsequent call. That skips both a re-parse and the FFI parse round-trip.

Memoize tokens() at the consumer boundary. If you're inside a reactive UI, a useMemo (or equivalent) keyed on the source string is enough — there is no benefit to invalidating the memo until the source actually changes.

If you're producing tokens from your own data model

Tree-shaped editors that maintain their own document state can flatten their tree into the JS Token shape and lint/format/diff against the engine without ever round-tripping through a USFM string. Fill in id, kind, source, and whichever optional fields apply.

If you're parallelizing work in Rust

The library is single-threaded. Parallelize at the file / document level with rayon — see benches/parallelism.rs for the pattern.

Read order#

For a quick orientation to the codebase, read in this order:

  1. src/lib.rs — re-exports defining the public surface. Two pages.
  2. src/api.rs — the facade. Usfm → ParsedUsfm → TokenStream is the user story.
  3. src/token.rs — what a Token actually is. TokenData is the variant zoo.
  4. src/walker/mod.rs — visitor trait, scope stack, precedence rules. Module-level docs narrate the three design choices.
  5. src/marker_defs.rs — the type-level catalog (no data here, just shapes).
  6. src/lint_impl.rs — the largest visitor. LintCode at the top is the stable surface.
  7. crates/usfm_onion_wasm/src/lib.rs — the FFI layer. WalkToken's doc comment explains the boundary between FFI types and walker types.
